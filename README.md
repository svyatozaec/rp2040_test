# Linear Allocator with UART Packet Logging

A bump (linear) memory allocator for bare-metal targets, demonstrated on a
Raspberry Pi Pico (RP2040), with a binary UART logging protocol and a
desktop-side receiver.

## Design

A linear allocator serves allocations by advancing a cursor through a
pre-reserved buffer. Allocation is a bounds check plus a pointer increment -
constant time, no free-list traversal, no per-block headers, no fragmentation.

The cost of that speed is that individual allocations cannot be released. Memory
is reclaimed in two ways:

- **`reset()`** - returns the allocator to its initial empty state.
- **`rewind(mark)`** - returns the cursor to a previously saved point, freeing
  everything allocated after it in one operation. This is LIFO: marks must be
  released in the reverse order they were taken.

### Stale mark detection

`reset()` increments a generation counter, which is also stored in every `Mark`.
A `rewind()` using a mark taken before a reset is rejected rather than silently
corrupting the cursor. This turns a use-after-reset bug into a returned `false`.

### Freed memory poisoning

`reset()` and `rewind()` fill the released region with `0xDD`. A pointer read
after release yields an obviously-wrong value instead of stale-but-plausible
data. This makes pointer invalidation directly observable - see the demo.

## API

```cpp
void      init(uint8_t* buf, size_t size);

void*     alloc(size_t size, size_t align = 4);
template <typename T, typename... Args> T* allocObject(Args&&... args);
template <typename T>                   T* allocArray(size_t count);

Mark      mark() const;
bool      rewind(Mark m);          // false if the mark is stale or invalid
void      reset();

size_t    used() const;
size_t    freeSpace() const;
size_t    highWater() const;       // peak usage, survives rewind
size_t    capacity() const;
```

`allocObject` and `allocArray` derive alignment from `alignof(T)`, so callers do
not have to reason about it. Objects are constructed in place with placement new.

## Log packet format

Little-endian throughout.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 1 | `SYNC` | `0xAA` |
| 1 | 1 | `LEN` | length of the body: `5 + payload` |
| 2 | 4 | `TIMESTAMP` | milliseconds since boot |
| 6 | 1 | `SEVERITY` | 0=DEBUG, 1=INFO, 2=WARN, 3=ERROR |
| 7 | LEN−5 | `PAYLOAD` | ASCII message, max 200 bytes |
| 2+LEN | 2 | `CRC16` | CCITT, poly `0x1021`, init `0xFFFF`, over `TIMESTAMP`..`PAYLOAD` |

The receiver scans for `SYNC`, reads `LEN` bytes of body plus 2 CRC bytes,
validates the CRC, and drops the frame on mismatch.

**Known limitation:** the sync marker is a single byte with no escaping, so a
`0xAA` occurring inside a timestamp will occasionally be mistaken for a frame
start. The CRC check rejects the resulting frame and the stream resynchronises on
the next real boundary, so the failure mode is an occasional dropped message
rather than corrupted output. A two-byte sync word (`0xAA 0x55`) plus byte-wise
rescan on CRC failure would eliminate it.

## Hardware

Raspberry Pi Pico (RP2040) and an FTDI TTL-232R-3V3 cable.

| Cable wire | Signal | Pico pin |
|---|---|---|
| Yellow | cable RXD | pin 1 - GP0 / UART0 TX |
| Orange | cable TXD | pin 2 - GP1 / UART0 RX |
| Black | GND | pin 3 - GND |

Leave the red (3V3), brown (CTS) and green (RTS) wires unconnected - the board is
powered over USB, and back-feeding 3.3 V risks supply contention.

UART0 at 115200 baud, 8N1.

## Demonstration sequence

The firmware loops through the following, blinking a distinct LED pattern and
emitting a log packet at each step.

1. **Alignment verification** (on a separate 256-byte arena). For alignments 1,
   2, 4, 8 and 16, a 1-byte allocation deliberately misaligns the cursor, then an
   aligned allocation is made and the returned address is logged along with
   `ptr % align`. Followed by an `alignof`-driven `allocObject<uint64_t>`.
2. **Byte allocation** of 512 bytes; the byte `0x42` is written through the
   returned pointer.
3. **Typed allocation** - `allocArray<uint32_t>(64)`, written across its full
   extent and read back, then `allocObject<Point>{7, 42}`.
4. **Exhaustion** - the arena is filled until a 1536-byte request cannot be
   satisfied. The allocator returns `nullptr` and logs at ERROR severity; it does
   not fault or trap.
5. **Bulk free** - `rewind()` to the saved mark releases 2048 bytes in one
   operation, after which the *same* 1536-byte request succeeds. This is the
   evidence that the release actually reclaimed the space.
6. **Reset and pointer invalidation** - after `reset()`, the address written in
   step 2 is read back. It reports `0xDD` rather than `0x42`, showing the earlier
   pointer no longer refers to valid data.
7. **Stale mark rejection** - a `rewind()` with a mark taken before the reset is
   refused.

### Arena accounting

Arena size 4096 bytes.

| Step | Size | `used` | `free` | |
|---|---|---|---|---|
| alloc 512 | 512 | 512 | 3584 | |
| allocArray\<uint32_t\>(64) | 256 | 768 | 3328 | |
| allocObject\<Point\> | 8 | 776 | 3320 | |
| *mark taken* | - | 776 | 3320 | |
| alloc 1024 | 1024 | 1800 | 2296 | |
| alloc 1024 | 1024 | 2824 | 1272 | |
| alloc 1536 | - | 2824 | 1272 | fails: 1536 > 1272 |
| rewind to mark | −2048 | 776 | 3320 | |
| alloc 1536 | 1536 | 2312 | 1784 | identical request, now succeeds |

Peak usage (`high`) settles at 2824 bytes.

### LED patterns

| Pattern | Meaning |
|---|---|
| 1 long blink | operation succeeded |
| 3 short blinks | operation failed |
| 2 medium blinks | rewind performed |
| 4 short blinks | invalid operation correctly rejected |
| 1 very long blink | allocator reset |

The `used` and `free` values match the accounting table above exactly. Three
things in this capture are worth pointing out:

- The 1536-byte request fails at `free=1272`, then the identical request
  succeeds after the rewind releases 2048 bytes.
- `high=2824` persists across the rewind and the reset, since peak usage is a
  high-water mark rather than a live measurement.
- `alloc()` costs 1–2 µs and is independent of the requested size or of how many
  allocations preceded it. `rewind()` (9–16 µs) and `reset()` (18–21 µs) are
  slower only because they poison the released region with `memset`; the cursor
  update itself is a single assignment.

## Alignment bug found by on-target testing

The first implementation applied the alignment rounding to the *offset within the
arena* rather than to the resulting address:

```cpp
size_t start = alignUp(offset_, align);   // wrong
```

This is only correct when the arena's base address is itself at least as aligned
as the request. `uint8_t[]` carries an alignment requirement of 1, and the linker
placed the test arena at an address congruent to 8 mod 16. Requests for 1-, 2-,
4- and 8-byte alignment passed by coincidence; the 16-byte case returned
`0x200005A8`, which is 8 mod 16.

The fix aligns the absolute address and converts back to an offset, which is
correct for any base address:

```cpp
uintptr_t aligned = alignUp(reinterpret_cast<uintptr_t>(base_) + offset_, align);
size_t    start   = aligned - reinterpret_cast<uintptr_t>(base_);
```

`alloc()` additionally rejects non-power-of-two alignments, whose bitmask
arithmetic would otherwise produce a silently wrong result, and the bounds check
was rewritten as `start > capacity_ - size` to avoid integer overflow on a large
`size`. The arenas are declared `alignas(16)` as well, which does not affect
correctness but avoids wasting padding bytes in the common case.

This is worth recording because it is the class of defect that only appears on
the target: the same code aligned correctly on a host where the buffer happened
to land on a 16-byte boundary.

## Limitations and trade-offs

- **No individual `free()`.** Inherent to the design. Memory is released by
  `rewind()` or `reset()` only.
- **`rewind()` is LIFO.** Marks must be released in reverse order of acquisition.
- **Destructors are never run.** `rewind()` and `reset()` only move the cursor, so
  a type that owns a resource will leak it. Intended for trivially-destructible
  types; the caller is responsible for anything else.
- **Not thread- or interrupt-safe.** Concurrent use requires external
  synchronisation - a `critical_section_t` on the RP2040 if allocating from an
  ISR.
- **Alignment padding is charged to the arena.** A workload mixing alignment
  requirements wastes some capacity to padding.
- **Logging is blocking.** `uart_write_blocking` stalls until the frame is out,
  which at 115200 baud is roughly 6 ms for a 70-byte packet. Acceptable for a
  demonstration; a production build should buffer and transmit via DMA or an
  interrupt-driven queue.
